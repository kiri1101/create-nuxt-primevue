# Nuxt 4 + PrimeVue 4 + Tailwind 4: the silent traps

Most failures in this stack raise no error. The build passes, the console is empty, and all you have is "it doesn't work". This guide lists the licence change that catches most people first, then thirteen other problems, each as symptom, cause and fix. The exact error text is in the heading or the first line, so you can paste it into a search engine.

The versions this guide was checked against: Nuxt 4.x, Vue 3.5, PrimeVue 4.5.5, Tailwind CSS 4.3, the Node versions Nuxt supports (today `^22.22.3 || ^24.15.0 || >=26.0.0`). If your versions differ a lot, check the official documentation: it is more current than this file.

## The licence change

### What changed

PrimeVue 4.x is MIT. From PrimeVue 5.0.0, PrimeTek publishes the library under its commercial PrimeUI licence, and the library expects a licence key. Without a key it shows a fixed red badge on every page (see [trap 5](#5-invalid-primeui-license-red-badge)).

This is PrimeTek's decision to make, and the terms are theirs to set. This guide only records what it means for your install command. As of 2026-11-06, `npm install primevue` installs 5.x.

Only the newest versions are affected. Older releases stay MIT on the registry and keep working.

| Package | `latest` (not MIT) | Last MIT version |
|---|---|---|
| `primevue` | 5.0.4 | **4.5.5** |
| `@primevue/nuxt-module` | 5.0.4 | **4.5.5** |
| `@primeuix/themes` | 3.1.0 | **2.0.3** |
| `primeicons` | 8.0.2 | **7.0.0** |

`tailwindcss`, `@tailwindcss/vite`, `tailwindcss-primeui` and `nuxt` are MIT and are not affected.

`@primeuix/themes` 2.0.3 works with `primevue` 4.5.5. The template this CLI generates uses exactly that pair. `@primevue/themes`, the older theme package name, is deprecated: use `@primeuix/themes`. The packages under the `@primeuix` scope are not all commercial: only the newest versions are.

### How to check what you have

A package is free to use here only if its `license` field is exactly `MIT`.

```bash
npx create-nuxt-primevue doctor --check
```

It scans every installed `primevue`, `primeicons`, `@primevue/*` and `@primeuix/*` package, including nested copies under pnpm, Yarn and Bun layouts. It exits 1 if any is not MIT. Projects generated by this CLI also run the same check before every build (`npm run check:licences`).

### How a non-MIT package gets in

Exact pins mean `npm update` alone does not bring in a non-MIT Prime package. The real risks are:

- `npm i primevue@latest` (or `npm install primevue` in a project that did not have it yet);
- a hand-edited version in `package.json`;
- another dependency that pulls in a v5 package.

A tutorial written for v5 is a common way the first two happen, because the theme package name and import paths differ between lines.

### Going back to v4

```bash
npx create-nuxt-primevue doctor
```

`doctor` shows the pins it would rewrite, asks, and only writes in a git repository with a clean working tree. It never commits. If you prefer to do it by hand, pin the four packages in the table above to their last MIT versions, with no `^` or `~`, delete `node_modules` and the lockfile, and reinstall. Then run the check.

Going back can break code that uses features only present in v5.

### The trade-off of staying on v4

- You stay on free, MIT-licensed software with no key to manage.
- You get no new v4 features. Check PrimeTek's own announcements for how long 4.x will receive fixes.
- You cannot use anything that exists only in v5.

### When paying for v5 is worth considering

- You want the newest components and fixes, and the licence terms fit your project.
- Your organisation already buys software with support, and a licence key is a small cost.
- You do not qualify for the free Community tier.

When this guide was written, the Community licence was described as free for organisations with fewer than 5 developers, fewer than 10 employees and under $1M in revenue, and as excluding public-sector organisations. The last condition matters if you build for a government body or a public university. Check PrimeTek's current terms (https://primeui.dev/licenses) rather than relying on this summary: they can change, and this guide may be out of date.

If you buy a licence and move to v5 on purpose, the guard in a generated project will fail the build, because it only accepts MIT. To remove it, delete `scripts/check-licences.mjs`, the `node scripts/check-licences.mjs &&` at the start of the `build` script, and the `check:licences` script in `package.json`.

If you do hold a key, `doctor` asks about it and leaves your packages alone (unless you pass `--yes-fix`, which skips the question and applies the fix).

## 1. Tailwind is installed but its classes do nothing

**Symptom:** utility classes have no effect. No error, no warning, and the build passes.

**Cause:** Tailwind 4 on Nuxt needs two things, and reports neither when one is missing:

```ts
css: ['~/assets/css/main.css'],     // loads the stylesheet
vite: { plugins: [tailwindcss()] }, // compiles Tailwind
```

With only the plugin, nothing imports the stylesheet, so Tailwind emits nothing. With only the `css` entry, the sheet is loaded but never compiled.

**Fix:** set both. The stylesheet starts with `@import "tailwindcss";`.

**Check:** after `npm run build`, a compiled CSS file usually carries Tailwind's version comment. If none does, search for a utility class you used instead.

```bash
grep -l 'tailwindcss v4' .output/public/_nuxt/*.css   # usually lists a file
grep -l 'some-utility-you-used' .output/public/_nuxt/*.css
```

## 2. PrimeVue is installed but components do not render

**Symptom:** `[Vue warn]: Failed to resolve component: Button`, or components simply do not appear.

**Cause:** `npm install primevue` configures nothing. You need the Nuxt module and a theme in `nuxt.config.ts`. Same class of problem as trap 1: the package is there, the configuration is not.

**Fix:** add `@primevue/nuxt-module` to `modules` and give it a theme preset. The generated project does this, with the theme kept in `app/theme.ts`:

```ts
export default defineNuxtConfig({
  modules: ['@primevue/nuxt-module'],
  primevue: { importTheme: { from: '~/theme.ts' } },
})
```

A habit that helps on this stack: after any install, open the config before you write code. An installed package is not a configured package.

## 3. A Tailwind class on a PrimeVue component does nothing

**Symptom:** `<Button class="bg-red-500">` does not change the colour, and the only thing that works is `!important`.

**Cause:** CSS layer order. Without a `cssLayer` setting, or with the wrong order, PrimeVue's styles win over Tailwind's utilities.

**Fix:** put PrimeVue in its own layer, after `theme` and `base` and before `utilities`:

```ts
options: {
  cssLayer: {
    name: 'primevue',
    order: 'theme, base, primevue, components, utilities',
  },
}
```

If you find yourself reaching for `!important` (or Tailwind's `!` suffix) on a PrimeVue component, treat it as a sign the layers are in the wrong order. Fix the order instead of stacking overrides. `doctor` warns when it finds no `cssLayer` setting. Also make sure `tailwindcss-primeui` is installed and imported, which PrimeVue's Tailwind integration needs.

## 4. `grep p-button` finds nothing in the build

**Symptom:** `grep p-button .output/public/_nuxt/*.css` returns nothing, and you conclude the install is broken.

**It is not a bug.** PrimeVue's styled mode generates its CSS at runtime from the theme tokens and injects it into `<style>` tags. A search of the static bundle finds zero matches on a healthy install.

**What to do:** the only valid test is to run the app and fetch a page.

```bash
npm run build
PORT=3123 node .output/server/index.mjs     # in a second terminal
curl -s http://localhost:3123/ > page.html
grep -c 'p-button' page.html            # more than 0: components rendered
grep -c '@layer primevue' page.html     # more than 0: the layer setting is active
```

This does not prove the licence is fine. The badge may be added in the browser, inside a closed shadow root, so a text search of the server HTML can miss it even on v5. To check licences, run `npx create-nuxt-primevue doctor --check`. For a visual check, open the page in a browser and look for the badge, or for the `[PrimeUI]` message in the console.

This generalises: in this stack most breakage is invisible at build time. Prefer a running page over a passing build when you are proving something works. Stop the server when you are done.

## 5. "Invalid PrimeUI License" red badge

**Symptom:** the console shows `[PrimeUI] PrimeUI license is not configured.` and a red badge sits fixed at the bottom right of every page.

**Cause:** one or more Prime packages are on a version that needs a licence key (see [The licence change](#the-licence-change)). The badge is a `div` with the id `p-license-host`, inside a closed shadow root, at `z-index: 2147483647`. No CSS can reach it or hide it, by design. Do not try to remove it: this guide does not cover that, and it is not what the check is for.

**Fix:** go back to the last MIT versions, or obtain a licence. Then check every Prime package, including ones installed by other packages:

```bash
npx create-nuxt-primevue doctor --check
```

Or by hand:

```bash
for d in node_modules/primevue node_modules/@primevue/* node_modules/@primeuix/*; do
  [ -f "$d/package.json" ] && node -e "
    const j=require('./$d/package.json');
    console.log((j.license==='MIT'?'OK ':'!! ')+j.name+' '+j.version+' '+j.license)"
done
```

## 6. npm warns about unapproved install scripts for esbuild

**Symptom:** on every install, npm warns that `esbuild` has an unapproved `postinstall` script and suggests approving it. The wording depends on your npm version; npm 11.19 accepts both `npm install-scripts approve <pkg>` and `npm approve-scripts <pkg>`.

**Usually you do not need to approve it.** esbuild ships its binary as an optional dependency (`@esbuild/<platform>`), which installs without running a script. Its install script is only a fallback for platforms where that binary does not exist.

**Check before you decide.** This works for any package:

```bash
./node_modules/.bin/esbuild --version   # if it answers, the script was not needed
```

A package that compiles native code (`sharp`, `better-sqlite3`) really needs its script. A package that uses the prebuilt-binary-as-optional-dependency pattern does not. Also note that approving all pending scripts at once approves everything waiting, not just the package you looked at.

## 7. `--shadow-…` is missing from the compiled CSS

**Symptom:** you define `--shadow-card` in `@theme`, then `grep -- '--shadow-card'` on the bundle finds nothing, although `.shadow-card` works.

**It is not a bug.** Tailwind 4 emits colour tokens as CSS variables but inlines shadow values into the utility. Search for `.shadow-card{`, not for `--shadow-card`.

## 8. Dark mode is half applied

There are two cases.

**If your project has dark mode (the case this template sets up).** One selector has to drive both libraries, or one of them follows the system setting and the other does not. The generated project uses:

- `@nuxtjs/color-mode` with `classSuffix: ''` and preference `system`, so the choice is stored and there is no flash on server-rendered pages;
- PrimeVue `darkModeSelector: '.dark'`;
- Tailwind `@custom-variant dark (&:where(.dark, .dark *));`.

**If your project is light only.** Symptom: the page stays light, but form fields, dropdown lists and scrollbars turn dark and the page looks broken. Cause: when the user's system is set to dark, the browser switches its native controls to dark and PrimeVue switches its components to dark too, whether or not you wrote any dark styles. Deleting your own dark styles changes neither. Fix: disable it at both levels.

```ts
// PrimeVue options
darkModeSelector: false,
```

```css
:root { color-scheme: light; }
```

Without the second part, the browser can still invert native form controls and scrollbars.

## 9. Fonts work in dev and vanish in production

**Symptom:** the fonts show in development and are gone in production.

**Cause:** the font files sit in `app/assets/` and `@font-face` points at a hard-coded URL. Vite adds a hash to asset file names in production, so the URL no longer resolves.

**Fix:** serve fonts from `public/fonts/`, where paths stay the same in source, dev and production. This also keeps your site from depending on a third-party font host. Check after a build:

```bash
ls .output/public/fonts/
grep -o '/fonts/[a-z-]*\.woff2' .output/public/_nuxt/*.css | sort -u
```

Preload only the subsets a page uses. If you take fonts from the Google Fonts API, request them with a browser User-Agent or you receive TTF instead of WOFF2. A variable font is one file for every weight, so declare one `@font-face` rule with `font-weight: 100 900` rather than one rule per weight.

## 10. Persisted state silently stops being saved

This one does not depend on PrimeVue, but it bites the same projects.

**Symptom:** a cart, a long form or saved preferences stop being remembered once they get large. No error, no warning.

**Cause:** the Nuxt module of `pinia-plugin-persistedstate` stores state in a cookie by default, not in `localStorage`. A cookie is readable on the server, so the state is already there at server render time and there is no hydration mismatch to manage. But cookies are limited to about 4 KB, and above that the browser drops the cookie without telling you.

One measurement, on a shopping cart storing only references and quantities (no labels or prices):

| shape | capacity before overflow |
|---|---|
| named objects | about 39 distinct lines |
| tuples with short keys | about 85 distinct lines |

Size grows with the number of distinct lines, not with quantities: 50 copies of one item cost one line.

**How to choose:**

- Use a cookie when the state is small and bounded, and when rendering it on the server matters (an indexable header badge, a public page).
- Use `localStorage` when the state can grow: `persist: { storage: piniaPluginPersistedstate.localStorage() }`. There is no practical size limit, but the server cannot see it, so anything that depends on it goes inside `<ClientOnly>` (see [trap 11](#11-clientonly-makes-the-page-jump)).

A failure you can see in development is better than one only a user sees in production. The cookie fails silently, often at the worst moment. `localStorage` costs a brief flash that you notice on the first try.

Whichever you pick, persist references and quantities only, never a label, price or image. Those are looked up again from the catalogue. Persisted state that freezes a price ends up showing a stale price.

## 11. `<ClientOnly>` makes the page jump

**Symptom:** the hydration warning is gone, but the block pops in and pushes the rest of the page down.

**Cause:** `<ClientOnly>` without a `#fallback` renders nothing on the server. There is nothing to mismatch, but the block has no height at first render and then takes its real size. You have traded a console warning for layout shift, which Core Web Vitals measure and users notice.

**Fix:** always give a fallback with roughly the same dimensions as the real content.

```vue
<ClientOnly>
  <CartSummary />
  <template #fallback>
    <div class="h-24 animate-pulse-soft rounded bg-surface-200" role="status">
      <span class="sr-only">Loading cart</span>
    </div>
  </template>
</ClientOnly>
```

Give the placeholder `role="status"` and visually hidden text, or screen readers meet an empty area. Respect `prefers-reduced-motion` on the animation; the generated project's custom animations already do.

## 12. `npm run build` exits with 255 in PowerShell

**Symptom:** `npm run build` returns exit code 255 although the build finished normally and `.output/` is complete.

**Cause:** Windows PowerShell 5.1 wraps each stderr line of a native program in an `ErrorRecord` and sets `$?` to `$false`, even when the program returned 0. A line such as `npm run build 2>&1 | Select-String …` triggers exactly this, and Nuxt writes deprecation warnings to stderr on every build.

**Fix:** run builds from Bash, or without redirecting stderr in PowerShell. From Bash:

```bash
npm run build > build.log 2>&1; echo "exit=$?"
tail -25 build.log
```

Related: searching a Nuxt build log for `error` also finds `error-404.mjs` and `error-500.mjs`, which are normal build output. Filter them out first: `grep -viE 'error-(404|500)'`.

## 13. `does not provide an export named 'mergeKeys'` on Windows

**Symptom:** the build passes, then every page returns HTTP 500 and the server log shows:

```text
import { mergeKeys } from '@primeuix/utils/classnames';
SyntaxError: The requested module '@primeuix/utils/classnames' does not provide an export named 'mergeKeys'
```

**Cause:** the project was built from a Windows 8.3 short path, such as `C:\Users\RUNNER~1\AppData\Local\Temp\...`, and the build wrote the wrong import. `mergeKeys` lives in `@primeuix/utils/object`, and your installed packages are fine. On a GitHub Windows runner, the same project failed from the short path and worked from the long one. The step inside the build that writes the import has not been traced, so treat the short path as the proven trigger, not the full explanation.

**Fix:** build from the long path. This mostly happens in CI scripts that build under the temp folder, because `os.tmpdir()` can return the short form there. Ask Node for the long one:

```js
import { realpathSync } from 'node:fs'
import { tmpdir } from 'node:os'

const temp = realpathSync.native(tmpdir())
```
